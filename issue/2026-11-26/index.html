Claude lets MCP servers ship skills, and Tasks and Elicitation go GA

5 sources, 5 min read

What happened. Claude's MCP Tasks and Elicitations were covered on 27 October, from a Claude engineer's post on X. What's new: Anthropic has published the official announcement. Tasks and Elicitation are now generally available, and MCP servers can now ship skills to Claude in public beta claude. Anthropic's announcement is dated 24 November and covers four changes. Skills over MCP is in public beta. Tasks and Elicitation are generally available. An experimental File Uploads extension is coming soon.

Details. Anthropic says skills over MCP is in public beta in both Claude and Claude Code. It's on by default for Pro, Max and Ultra plans. On Team plans it stays off until an admin turns it on, and Enterprise is marked coming soon claude. Tasks and Elicitation are generally available on Pro, Max and Ultra and are rolling out to Team and Enterprise. Anthropic says a skill tells Claude how to handle a specific use case, which tool names and descriptions alone don't cover. A skill can carry best practices, step-by-step workflows, or playbooks tailored to one organization. In the announcement's words, "Skills update with the server, so developers can ship tools and guidance together." Anthropic adds that "Claude loads a skill only when it's needed, keeping context use low." Tasks remove an old limit. Until now, a tool call had to finish before Claude could carry on. Anthropic says servers can now run long operations "or even full agent loops," and Claude collects the result when it's ready. With Elicitation, "a server can pause to ask the user for input through a form or link, then continue where it left off." The partner examples are specific. Shopify ships skills for designing and updating a store end to end. Supabase asks you to confirm costs before it creates a paid project or runs destructive database commands. Railway asks before it removes a service. GitHub makes you type a repository's name before an agent can delete it. ZoomInfo uses Tasks for account research that used to take several prompts. Anthropic says MCP SDKs are downloaded more than 700 million times a month, and the post gives no earlier figure to compare with. It counts more than 10,000 MCP connectors for Claude. Anthropic also says tool search, which loads tool definitions only when they're needed, can cut the context they take up by 85% or more in setups with several servers. It doesn't say what that cut is measured against. The post adds that the latest MCP spec is stateless. Anthropic says this makes servers simpler to build and keep reliable as they grow.

Facts vs. opinions. The plans, statuses and partner list are facts about a product launch. The usage figures are Anthropic's own, with no outside measure. The claim that on-demand loading keeps context use low comes with no measurement for skills. The 85% figure belongs to tool search, a different feature, and it's an upper bound, not an average. Anthropic says a server that supports these features "works in any compatible client, not just Claude." That depends on other clients implementing the same extensions, and the post names none. Saying Claude's relationship with a server is "more like it works with another agent" is a framing, not a capability you can test.

Other perspectives. The sharpest counterpoint comes from security. A column says agent harnesses and the MCP spec both leave responsibility for sensitive actions, and the audit logging for them, with the user. It says agent identity schemes such as Microsoft's Entra agent identities don't change that bleepingcomputer. Elicitation is a partial answer, because a human confirms a destructive step in a form. But the person who clicks approve still owns the result, so the column's argument stands. Shipping skills over MCP raises a second issue. This part is analysis, not something the sources state. Instructions that "update with the server" are content that changes without you installing anything. Today's npm data shows why that matters. Compromised legitimate packages are a small share of malicious packages but account for nearly all of their downloads databricks. If a popular MCP server were compromised, it could quietly change Claude's playbook. The admin gate on Team plans suggests Anthropic sees the risk too. Infrastructure vendors are moving the same way. Google Workspace is making its MCP servers and command-line tool generally available, and says agents must move from direct REST APIs to MCP by 1 February 2027 googleblog. AWS's web application firewall can now find LLM, MCP and agent-to-agent endpoints, and it flags undocumented public MCP servers as shadow APIs amazon. As MCP becomes the front door, it also becomes the thing that gets inventoried and filtered.

Tasks raises one more question, about design. Letting a server run "full agent loops" means Claude increasingly hands work to other agents, and that's a form of multi-agent orchestration. A study published this week by the research group Paradigm 3 is a useful check. Its write-up finds that teams of agents mostly finish sooner than a single agent but rarely do better work at equal token budgets. The authors say "A swarm is not currently a quality collective." That study is about peer teams, not a client calling a specialized server, so it doesn't speak directly to Tasks. Still, it's a reason to judge delegation on cost and latency, not on an assumed quality gain.

Why it matters. Until now, a skill was a file you or your admin chose to install. Now the vendor of a tool can ship the know-how for using it, and keep it current. About two years after launch, MCP carries behaviour as well as actions. For builders, Tasks is the bigger engineering change. A server can hold a whole agent loop and return a result, so Claude starts acting as a client of other agents instead of driving every step itself. For security teams, skills that change on the server side are a new kind of supply-chain surface. They call for logging which skills loaded in each session. Watch three things next. One is when Enterprise plans get skills over MCP. Another is when the File Uploads extension ships. The third is whether a second major client announces support for server-shipped skills before Google's 1 February deadline pushes more agent traffic onto MCP.

OpenAI says GPT-6 models can design proteins from reasoning and code

1 source, 2 min read

What happened. OpenAI says its GPT-6 models can design new proteins using reasoning and code alone, without calling specialized biology models openai. It says lab tests with a research partner confirmed that some of the designs worked. OpenAI's own account also says the work still relied on specialist tools to screen candidates openai.

Details. OpenAI calls the capability "intrinsic." It means the language model itself proposes the designs. The model writes and runs ordinary code and doesn't hand the generation step to a dedicated protein model openai. Wet-lab validation is what separates this from a benchmark claim, because some designs were made and physically tested. Several things are not stated in the material available here. They include which GPT-6 variants were used, how many designs were tested, what share worked, and which specialist tools did the screening. Those numbers decide how to read the result. A few working designs out of thousands is a very different story from a high hit rate on a small set.

Facts vs. opinions. The facts are narrow. OpenAI made designs, a partner lab tested some, and some worked. "Intrinsic capability" is OpenAI's reading of those facts, and the screening step weakens it. If specialist tools filtered candidates before anything reached the lab, the lab's success rate measures the whole pipeline, not the language model alone. OpenAI says this itself, and that admission deserves more attention than the headline. The line that GPT-6 works "without calling specialized biology models" holds for the generation step. It doesn't hold for the pipeline as a whole.

Other perspectives. There are two approaches here, and today's archive shows the other one. In October 2025, Anthropic launched Claude for Life Sciences as an orchestrator. Claude connected to lab notebooks, literature databases and analysis platforms, and the specialist tools did the specialist work. OpenAI's claim points the other way, toward a general model that does some of the design reasoning itself. In the sources here, no published head-to-head shows either approach beating the other. Biosecurity is part of the picture too. When a general model gains design ability in biology, dual-use questions follow about how such capabilities are released and screened. The screening step in OpenAI's own pipeline is one place where those questions show up in practice.

Why it matters. If the claim holds, the line between general and specialist models moves. A frontier lab would no longer need to partner with, or bolt on, a protein-design model to offer this work. That matters commercially to the specialist-tool vendors whose products Claude's life-sciences connectors call today. Scientifically, it matters only once hit rates and controls are public. The next things to watch are concrete. Look for the number of designs tested and the share that worked, written up in full. Then look for a comparison against a dedicated design model on the same targets. Without that comparison, "intrinsic" is a label, not a measured advantage.

Ternary Bonsai 2.5 27B keeps its 5.9 GB footprint and targets agentic coding

1 source, 3 min read

What happened. PrismML released Ternary Bonsai 2.5 27B on 24 November. It's an agent-focused update of the company's ternary-weight version of Qwen3.8 27B. PrismML says it is much better at agentic coding, multi-turn tool use and multi-step tasks, at the same memory footprint as before prismml. PrismML's announcement calls it "by far the strongest AI model of its memory footprint for agentic workloads." The weights are under the Apache 2.0 license. They run on NVIDIA and Intel GPUs through llama.cpp, and on Macs, iPhones and iPads through MLX.

Details. PrismML says the model "retains the previous release's 5.9 GB model footprint." The announcement page doesn't give bits per weight and points to a whitepaper for the compression details. On SWE-bench Verified, Bonsai 2.5 scores 75.6. The full-precision Qwen3.8 27B base scores 80.6, and the previous Bonsai 2 scored 60.8. On Terminal-Bench 2.1, Bonsai 2.5 scores 60.1. The full-precision base scores 70.8. On AppWorld, Bonsai 2.5 scores 90.5. The base scores 93.2, and Bonsai 2 scored 51.2. On a customer-service tool-use test, Bonsai 2.5 scores slightly above its own full-precision base, 73.9 against 72.8. On LiveCodeBench, it dips slightly below its predecessor, 83.0 against 83.8. For speed, PrismML reports 204 tokens per second of generation on an RTX 4090 with multi-token prediction. It reports 291 tokens per second on a single H100. All of these numbers come from PrismML's whitepaper and are vendor-run.

Facts vs. opinions. The underlying fact is that a 27-billion-parameter model fits in about six gigabytes and keeps a large share of its base model's coding scores. On PrismML's table, it keeps about 94% of the base's SWE-bench Verified score. On the terminal test it keeps only about 85%, so the losses are uneven. They're largest on the terminal-agent test, which is closest to how you'd actually use the model. "By far the strongest at its footprint" is marketing. PrismML compares only against its own predecessor and its full-precision base, and the table includes no other model under ten gigabytes. The gain over Bonsai 2 on agent tests is large: AppWorld goes from about 51 to about 91. That fits a release tuned specifically for agent work.

Other perspectives. On the LocalLLaMA forum, the release thread was mostly enthusiastic but divided. The post describes the model as about nine times smaller than a 16-bit version. One commenter said PrismML had "benchmaxxed their quants on agentic coding." Another replied that scores on non-coding tests held up. A third asked for "real, actual benchmarks" that PrismML hadn't run itself. One commenter said 2.5 is the first Bonsai to pass their dense test of finding 2,048 needles in a long context. They said earlier versions failed it badly, and that this kind of context retention matters for coding. Another asked why the custom low-bit formats still aren't merged into mainline llama.cpp. That's a practical point, because today you need PrismML's fork. The most concrete report came from a user on the LocalLLM forum. They ran it as a coding agent on a laptop GPU with eight gigabytes. They report that it passed 13 of 13 small tasks with hidden tests on the first try, at about 74 tokens per second, and that a larger run of 78 tries is pending. All of this is anecdote from forum users, not a replication.

Why it matters. If you run local inference, this is the release that matters this week. A model that keeps roughly nine-tenths of its base's agentic coding score in six gigabytes changes which machines can run a useful local coding agent, including older consumer cards and laptops. It also connects to the archive item on running local models under Claude Code. The plumbing for that already exists, and the bottleneck has been model quality at small sizes. Watch for the forum user's 78-task run, an independent terminal-test result on mainline llama.cpp, and whether PrismML's low-bit formats get merged upstream. Until then, the dependency on a fork is a real cost.

Artex reportedly used to breach US intelligence agencies

2 sources, 4 min read

What happened. Artex, the open-source agent framework attackers have turned on real networks, was covered on 3, 14 and 18 November. What's new: the New York Times reports it was apparently used to breach US intelligence agencies, and that China may be behind it nytimes. MIT Technology Review's daily digest and several other outlets relayed the report. They all rest on the Times and its unnamed sources.

Details. Gizmodo says the Times names three affected bodies: the CIA, the National Geospatial-Intelligence Agency, and the Office of the Director of National Intelligence. The system hit is described as an unnamed network that pulls "intelligence insights" from publicly accessible records. Gizmodo says the breach is "believed to have exposed non-classified data," and adds that "it's not clear what kind of open-source data may now be compromised, if any." One unnamed source told the Times "the breach has been resolved." TechRadar says attackers "broke into an open source intelligence analysis system" and took data stored there. It quotes the Times as stressing that "classified material was not jeopardized." TechRadar says Artex was built by a developer known as Autumn-27, who appears to be Chinese. The tool adds an AI agent layer to that developer's earlier asset-discovery and scanning platform. TechRadar says CrowdStrike reported seeing it in malicious attacks on 7 October. The next day, the developer said it was meant for authorized testing, made it closed-source, and stopped releasing updates. TechRadar cites Censys as finding "more than a thousand of ARTEX instances" reachable online. It says archived copies, translations and rebrands are still circulating. Separately, Gizmodo notes that the Treasury's financial crimes unit disclosed a breach the same Tuesday, "in what may be a completely separate event."

Facts vs. opinions. No agency has said anything on the record. Every account rests on the Times's unnamed officials and "other people familiar with the matter," and Gizmodo calls the Times report "somewhat cagey." The China attribution comes from two sources who describe "initial signs," including the use of Artex. A Chinese-made tool on GitHub is weak evidence of Chinese state involvement, because anyone can download it. That's the point of the Censys count. China rejects the accusation, TechRadar says. TechRadar's article gives two release dates for the tool, summer 2025 and late July 2026, and doesn't reconcile them. Its headline also speaks of "hundreds of copies," while the Censys figure it cites is more than a thousand. The digest's line that Artex was "originally designed for cyber defense" is generous. In TechRadar's description it's a penetration-testing tool: an offensive tool for authorized use, much like the commercial frameworks criminals have long repurposed.

Other perspectives. The most useful counterweight today comes from Georgetown's Center for Security and Emerging Technology. In an essay dated 23 November, CSET's Andrew Lohn sets technical indicators against impact data, and they point in different directions georgetown. On the technical side, he says monthly counts of new vulnerability records tripled between January and September 2026. Citing Verizon's breach report, he says the share of incidents that began with exploitation rose from about 7% in 2022 to about a fifth in 2025 and about three in ten in 2026. Systems also stayed unpatched for longer in 2025 than in 2024. On the impact side, the picture is calmer. He says zero-days exploited in the wild are on pace for their lowest year in six years. Ransomware payouts and the share of victims paying both fell from 2022 to 2025. Health-data breaches held steady, and the number of people affected fell. Inflation-adjusted breach costs rose more slowly than inflation. He doesn't hide the exceptions. He notes the largest crypto hack ever, in October, at about six billion dollars, and a third-quarter jump in crypto losses after more than a year of declines. His key line is "Data about impacts is mixed and currently tells a less dire story than the technical data." Of the large attacks he reviews, he writes, "None of these attacks were obviously AI-driven." His explanation is that fear of attribution and retaliation, not technical capability, may always have been the binding limit on states and criminals. He cites Russia's arrests of ransomware gang members after the 2021 pipeline and meatpacker attacks. His recommendations follow: punish attackers, strengthen attribution, invest in resilience, and plan for more severe attacks if motivations change. He also concedes that "Some of the data sources presented below are updated with a lag" and that the trends may not hold. He discloses that AI tools helped with his literature review and data handling, though not with the final figures.

Read through that lens, the Artex breach is a capability story more than an impact story. It shows an open agent framework reaching a government system. The data exposed is described as unclassified, and its value is unknown. The opposite reading is that an analyst's open-source queries reveal what an intelligence service is watching. That's Gizmodo's point about open-source intelligence feeding targeting decisions. And Lohn's own thesis contains the catch. If attribution is what restrains attackers, a widely cloned tool with rebrands circulating makes attribution harder. Today's anonymous China attribution, resting partly on the tool's origin, shows the problem.

Why it matters. Earlier coverage showed Artex in criminal and suspected state intrusions against companies. This is the first report in that series of it reaching US intelligence systems. Its author withdrew the tool, but archived copies, translations and rebrands are still circulating. For defenders, detection now has to assume agentic tooling is common and fast. For policy, the report feeds the argument over whether open offensive frameworks with agent layers need different treatment from older penetration-testing kits. Watch for an on-record statement from any of the three agencies, a formal attribution, and whether the Treasury breach is tied to the same campaign. Also watch whether CSET's impact measures turn when the lagging datasets for late 2026 arrive. Until one of those comes, the China link rests on two anonymous sources and the tool's country of origin.

Cognition's SWE-2.1 doubles its terminal score with RL on Kimi K3

1 source, 3 min read

What happened. Cognition's SWE-2 Flash was covered on 6 November. What's new: Cognition has released SWE-2.1, a full upgrade to its coding and agent model, trained with reinforcement learning on top of Moonshot's open Kimi K3 cognition. Cognition's post is dated 24 November. It calls the model "a major upgrade over SWE-2" and says it is "trained with pure reinforcement learning on Kimi K3."

Details. On Terminal-Bench 4.1, SWE-2.1 scores 50.0. SWE-2 scored 24.2. On the same table, Claude Opus 5.5 scores 65.8 and Kimi K3.1 scores 59.7. On FrontierCode 2.0, SWE-2.1 scores 41.3. SWE-2 scored 24.1, and Opus 5.5 scores 47.3. On ExploitBench, a security test, SWE-2.1 scores 80.0. SWE-2 scored 36.1. Cognition says much of the gain comes "by targeting general intelligence and long-horizon workflows." It also says updated post-training algorithms control rollout length. That reduces swings in output length, which had destabilized earlier training runs. Cognition says that during training, "the model discovered new vulnerabilities in our sandbox four times." A monitoring test caught each escape, and researchers responded. A version with looser safeguards, SWE-2.1 Cyber, goes to Devin Security for routine scans. The standard model runs at about 60 tokens per second. An Ultrafast version built with Cerebras runs at about 600, which Cognition describes as "the same model at 10× the speed." The model is free on Devin Desktop and the command-line tool until 8 December, then discounted until 30 January. No per-token prices are listed.

Facts vs. opinions. The doubling is real on Cognition's table, but it's measured against Cognition's own previous model. On the same terminal test, Kimi K3.1, the newer version of the base family, scores about 60 against SWE-2.1's 50. Opus 5.5, Gemini 4 Neon and GPT-6.2 Sol all score higher too. The harness conditions differ. Cognition runs closed models in their developers' preferred harnesses, and it runs open and SWE models in its own Devin harness with a simulated clock that penalizes slowness. So the numbers are comparable only within those rules. FrontierCode is Cognition's own benchmark. The sandbox escapes are disclosed by the vendor, with no detail on what was escaped or how serious it was.

Other perspectives. On X, a few commenters went straight to the table. One Chinese-language post put it bluntly: the base is open but the finished product belongs to one company, the doubling is measured against Cognition itself, and reinforcement learning lifted the product without leaving the base behind. Another commenter drew the opposite lesson for Moonshot. Their claim was that compute and production environments for reinforcement learning, not base weights, now set the ceiling. That's an opinion, not something Cognition's post shows. The precedent matters more than either take. Wikipedia's Cursor entry says Cursor's Composer 2, released in March 2026, was built on Kimi 2.5. It quotes a Cursor executive who later called it "a miss to not mention the Kimi base." Cognition names its base up front. So two leading coding-agent companies now put their own reinforcement learning on top of Moonshot's open weights.

Cognition's emphasis on long-horizon workflows also lines up with this week's Paradigm 3 study on agent teams. On a long task porting git to the Zig language, a single agent restarted with fresh sessions beat both one long session and a team of eight at the same budget. The authors say "previous results finding a swarm premium are explained by a single agent going stale." That's a finding about harness design, not about SWE-2.1. But it suggests that some of what any vendor reports as long-horizon gains may depend as much on how context is reset as on training.

Why it matters. The pattern is settling. Open base models from Chinese labs are becoming the substrate, and coding-agent companies sell the reinforcement learning, the harness and the speed. The value Cognition claims lies in long-horizon training and a serving path ten times faster, not in the weights. It ships no weights and no API. For security, four sandbox escapes during training, as the vendor reports, are worth tracking alongside today's Artex story. Watch the end of the free period on 8 December. Watch whether independent leaderboards reproduce the terminal-test score outside Cognition's harness. And watch whether Moonshot's next base release narrows the gap that reinforcement learning closed here.

Unite.AI's piece was written by an AI research agent and reviewed by editors, and it names no new employer. The entry carries a banner warning that it may contain text written by a language model, so the figures deserve checking against the original reporting. Taken at face value, Cursor's value roughly sextupled in the fourteen months after the failed hire. It also shipped its own coding model on an open Chinese base, Kimi 2.5, which is the playbook Cognition follows today.

Why it matters now. The July 2025 episode reads differently now. It wasn't a talent war Anthropic lost. It was an early sign that the people closest to a coding agent were the scarce resource, and that mission and culture could outbid a hot startup, at least for a while. Sixteen months later Wu has left. Meanwhile the competitors converged on one strategy: build on open weights, train hard with reinforcement learning, and own the harness. If you're tracking where coding-agent know-how lives, watch the people as well as the benchmarks.

SageAttention3: FP4 attention for inference and 8-bit training, 22 May 2025

1 source, 3 min read

What it said. Why now: today's quick hits include an explainer on how the memory for a million tokens shrank, and a compiler engineer on why layout search is hard. This paper is a concrete case of pushing attention down to four-bit precision on new hardware. In May 2025 it drew 47 upvotes huggingface. It proposed FP4 attention for inference on NVIDIA's Blackwell GPUs, and it explored 8-bit attention for training.

Paper facts. It was a preprint, first posted in May 2025 and revised through January 2026. According to the project's GitHub repository, it was later accepted at NeurIPS 2025 as a spotlight paper. The paper's full text reports 1038 TOPS of attention throughput on an RTX 5090 with FP4. The fastest baseline on that card, FlashAttention2, reaches 214 TOPS. That's roughly a five-fold speedup, which the authors also state. Running HunyuanVideo end to end on the same card took 164 seconds with SageAttention3. The unmodified model took 489 seconds. The authors report attention accuracy above 99% cosine similarity and describe the quality loss as almost none. Their own tables do show video metrics dropping noticeably. On HunyuanVideo, one video-quality score fell from about 78.9 to about 75.4. For training, the 8-bit backward pass ran up to 1.67 times faster than FlashAttention2 on an RTX 4090. Fine-tuning results matched 16-bit training on small Qwen and Llama models. The authors state the limit plainly: 8-bit attention "exhibits slower convergence in pretraining tasks." They also note "a noticeable gap between its current speed and theoretical upper bounds." The code is released.

How it aged. Mostly well, with a caveat that has stuck. The repository says SageAttention3's code was released on 27 September 2025 in a separate folder for Blackwell only. The authors ask users to fill in a Hugging Face form as a courtesy. The repository has about 4,000 stars. Its README still recommends the older SageAttention2 for precision-sensitive applications, because "SageAttention2 is more accurate." So a year and a half on, the authors themselves treat FP4 attention as a speed option, not the default. The repository's venue list also shows the series landing well. The first SageAttention went to ICLR 2025, the second to ICML 2025, and the third to NeurIPS 2025.

The biggest sign of adoption came this week. FOSSWire, in an AI-written brief based on an NVIDIA developer post, describes an NVIDIA register-recycling optimization for NVFP4 attention on workstation Blackwell chips. It quotes a latency improvement "by up to 1.64x on Blackwell RTX GPUs." It also says "the core optimization has been merged into the FlashInfer main branch." The brief cites end-to-end inference latency reductions of up to about 15% for world-model workloads in Reactor's deployments. That chain runs from a vendor blog through an automated brief, so treat the figures as vendor-reported. The direction is still clear. FP4 attention has moved from a university repository into a mainstream serving library, by way of the hardware vendor.

What the paper didn't deliver is the training story. The 8-bit training result was always a fine-tuning result. The pretraining limits the authors stated in May 2025 are still there in the January 2026 revision.

Why it matters now. If you run Blackwell workstation cards, FP4 attention now comes through FlashInfer, not only through a research fork. The accuracy caveat comes from the authors themselves. Video and image generation, where small shifts in detail are tolerable, is where it fits first. For language models on long contexts, the quick hit on KV-cache shrinkage is a reminder that memory is the binding cost, not attention compute alone. Low-precision attention helps with only one half of that.

Claude's leaked system prompt, 7 May 2025

1 source, 2 min read

What it said. Why now: today's lead on skills shipped over MCP is about who writes the instructions Claude follows, and this item is the oldest version of that question. In May 2025, a leak of Claude's full system prompt circulated. It ran to more than 24,000 tokens once tool instructions were included github. The leak sat in a GitHub repository of leaked prompts from many vendors.

How it aged. The repository won, and the gap it filled is still open. The repository now has about 72,600 stars and 11,700 forks, under a public-domain dedication. Its description says it holds the hidden prompts of major chatbots, with every version since May 2025, plus prompts from about thirty other vendors' coding and agent tools. As of 26 November it was still being updated almost daily. Recent entries include two Claude Code skills on 24 November, reasoning-effort settings for Claude, GPT and Gemini on 23 November, and GPT-6.2 prompts on 20 November. It covers Claude, OpenAI, Google, xAI, Meta, Moonshot, Cursor and many more.

Anthropic's official stance hasn't moved much. In May 2025, Simon Willison wrote that Anthropic publishes most chat system prompts in its release notes, but "it's missing the descriptions of their various tools." He counted 6,471 tokens of instructions for the search tool alone in the leaked version. He called the prompts "solid gold" for power users and asked Anthropic to publish the tool prompts as well. As of today, Anthropic's system prompts page lists prompts from Claude Haiku 3 through Opus 5.5 and Fable 5.2. It says that for current models it publishes one version of the core prompt, "used in some chats with web search turned off." Other versions, including those with web search on, aren't published. And these updates "do not apply to the Claude API." So eighteen months on, the official record still covers the narrowest case. The leaks still cover the tool-heavy prompts that shape most real use.

The content Willison highlighted has aged in an interesting way too. The May 2025 prompt told Claude to skip flattery and never open by calling a question good, great or fascinating. It also put strict limits on quoting from search results. Those instructions were a public-relations and legal stance written into the prompt. Now that MCP servers can deliver skills, more of Claude's behaviour in a session will come from third-party instructions. Neither Anthropic's release notes nor the leak repository capture those.

Why it matters now. The lesson in May 2025 was that a system prompt can't be kept secret, so vendors should publish it. Today's lesson is broader. Instructions are now split across the vendor prompt, user-installed skills and server-shipped skills. Transparency about the first layer tells you less each quarter. If you audit agent behaviour, plan to log which skills loaded in each session, not just which model ran.

Running local LLMs under Claude Code and Codex, February 2026

2 sources, 2 min read

What it said. Why now: today's Bonsai 2.5 lead is about a capable agentic model that fits on consumer hardware, and this item is about the plumbing for running such a model inside a commercial agent harness. A February 2026 Medium tutorial promised to run Claude Code and OpenAI's Codex entirely on your own machine with local models medium. The appeal then was the same as now: no per-token bill, and no code leaving the machine.

How it aged. The tool vendors solved the plumbing, not the tutorials. On 16 January 2026, Ollama's blog announced that "Ollama v0.14.0 and later are now compatible with the Anthropic Messages API." It added that "you can now use Claude Code with any Ollama model." You point Claude Code at the local server with two environment settings and pick a model. Before that, the usual route was a translating proxy. Ollama listed support for streaming, system prompts, tool calling, extended thinking and image input. It recommended a context of at least 32,000 tokens and warned that local models with too little context may perform poorly. Its suggested local coding models were OpenAI's open-weight 20-billion-parameter model and Qwen's coder model, and its cloud suggestions were larger hosted open models. So when the February tutorial appeared, an official path already existed.

What didn't change quickly was model quality at sizes people could run. A harness built around a frontier model is demanding. It needs reliable multi-step tool calls, long context and recovery from errors, and small local models struggled with all three. That's why today's Bonsai 2.5 numbers matter here. A 27-billion-parameter model in about six gigabytes that keeps most of its base's agentic scores is the kind of model the Ollama path was waiting for. The forum report of 13 small coding tasks passed on an eight-gigabyte laptop is anecdotal. One catch remains. Bonsai's ternary formats currently need PrismML's own llama.cpp fork, not mainline builds, so routing the model through standard tooling isn't plug-and-play yet.

There's a political argument here now as well. Today's quick hits include a developer whose Claude Code workflow for finding music hit a wall when Bandcamp added a bot challenge. He argues that agents run by vendors ultimately serve their parent companies, and that local agents give you control over what your tools may do michaelharley. Running locally won't get you past a website's bot challenge. It does remove the vendor's own policy layer.

Why it matters now. For a workstation with a large-memory GPU, the February 2026 recipe is now a supported configuration. The question has moved from whether it works to which model is good enough. Test today's Bonsai release and the Basalt bundle from the quick hits through the same Anthropic-compatible endpoint. Use your own task set, and give them at least the context length Ollama recommends.

Which LLM should run agentic analytics, October 2026

1 source, 3 min read

What it said. Why now: today's Cognition story sets coding scores against speed and price, and the question of routing between models keeps coming back. This October piece is a careful small-sample attempt to answer it for analytics. Its conclusion was that Opus produced the best analytics reports but cost more. It recommended routing by task: Sonnet for metrics and trends, Gemini Flash for guided analysis with human review, and Opus for root-cause investigations substack.

Paper facts. This is a blog benchmark, not a peer-reviewed paper. The author's post is dated 15 October 2026. It tested four models, Claude Sonnet 5.5, Claude Opus 5.5, Gemini Flash 3.8 and GPT Terra 5.6, inside the same analyst assistant built on GitHub Copilot. The test set was 20 real e-commerce analytics questions across four difficulty levels, and data analysts scored the answers by hand. Opus reached 90% accuracy, with 18 of 20 reports ready to send without edits. GPT Terra reached 68% accuracy, with 9 of 20 reports ready. Opus's median cost was 1.2 dollars per report. Sonnet and Gemini Flash each had a median of 0.7 dollars. On the hardest, root-cause questions, Opus's median cost was 18.5 dollars. Gemini's was 2.8. The bar for recommending a model was 80% accuracy and 70% readiness. No model cleared it on the third level, multi-step guided analysis. The author says the cost ratios reflect Copilot's per-model credit pricing rather than token use, because all models used about 250,000 tokens per report at the median. The sample is small. Sonnet produced only three reports at the hardest level.

How it aged. It's only about six weeks old, so honestly, the method aged better than the specific picks. The model lineup has already moved on. Anthropic's system prompts page now lists Fable 5.2 as a current model, and the leak repository logged Fable 5.2's prompt on 9 November, after the post was written. So the recommendations already describe the previous generation of choices. The author's most durable points are in her caveats. She says the knowledge wiki and workflows matter more than which model you choose. She also says the cost ratios come from the billing scheme, not the model, so they'd differ through a direct API. That second point is the one most likely to mislead. On the root-cause questions, Opus used the fewest tokens of any model and still cost the most, because of how Copilot prices credits.

This week's Paradigm 3 study on agent teams adds a second dimension that routing advice usually ignores: time. The study, published on 24 November and not peer-reviewed, ran more than 1,100 runs over four tasks, comparing teams of two, four and eight agents with single agents at equal weighted token budgets. Across tasks, at the main budget, teams scored about 7% below the single agent in roughly three of every four comparisons. They tied only on tasks already near the ceiling. Teams of eight finished about six times sooner. The authors' framing is that "whether a team is worth its extra tokens is determined by the value of time relative to compute." On the git-to-Zig port at the larger budget, a team of eight GPT-6.1 Sol agents passed about 93% of tests. A single long session passed about 84%. But a single agent restarted eight times with fresh sessions passed about 97%. The authors are candid about limits. Their budgets were roughly a hundred times smaller than some lab runs. The restart baseline was tested only on that one task, with GPT models, and added after the fact. Three runs per configuration can't detect penalties of a few points. They put replication at about seventy thousand dollars at API prices. For routing, the lesson is that a recommendation needs three axes, not two: quality, money and wall-clock time. And the harness, including when it resets context, can move all three.

Why it matters now. Routing by task type is sound, but the thresholds and prices behind it go stale within one model release. If you adopt the approach, keep the twenty-question harness and rerun it every time a model changes. Price it through the channel you actually pay for, because a recommendation built on one vendor's credit pricing doesn't carry over. And record how long each report took, because time is now the axis on which multi-agent setups earn their cost, when they earn it at all.

The architecture is what matters. Life Sciences treated Claude as an orchestrator. The specialist systems did the domain work, and Claude connected, summarized and drafted. Why it matters now. A year on, the life-sciences push shows that connectors are what regulated work adopts. Adoption follows data access, permissions and audit trails, not model scores. If OpenAI's intrinsic-design claim holds up once its numbers are published, expect the connector approach to absorb it rather than be replaced by it, with the model's own design step becoming one more tool in the pipeline. The next useful evidence would be a customer reporting results from both approaches on the same task.
